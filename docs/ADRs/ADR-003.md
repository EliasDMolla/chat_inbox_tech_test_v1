# ADR-003: Flujo de recepción del webhook y topología de RabbitMQ

**Estado:** Aceptado

## Contexto

Telegram envía los mensajes del bot mediante un webhook HTTP. La aplicación debe recibir esos mensajes, procesarlos, persistirlos y notificarlos al frontend en tiempo real.

Procesar toda la lógica dentro del request HTTP del webhook aumentaría el acoplamiento entre Telegram y el procesamiento interno, además de hacer que la respuesta a Telegram dependa de operaciones como acceso a base de datos, lógica de negocio y notificación por SignalR.

También es necesario contemplar reintentos, fallos temporales y posibles mensajes duplicados.

## Alternativas consideradas

### Procesamiento directo desde el webhook

El endpoint recibe el mensaje, ejecuta la lógica de negocio y persiste el resultado antes de responder.

**Ventajas:**
- Implementación simple.
- Menor cantidad de componentes.

**Desventajas:**
- Mayor tiempo de respuesta del webhook.
- Alto acoplamiento entre recepción y procesamiento.
- Un fallo en base de datos o lógica interna puede afectar la recepción del mensaje.
- Menor capacidad para absorber picos de tráfico.

### RabbitMQ entre el webhook y el procesamiento

El webhook valida mínimamente el update recibido, lo publica en RabbitMQ y responde rápidamente a Telegram. Un consumidor procesa posteriormente el mensaje.

**Ventajas:**
- Desacopla la recepción del procesamiento.
- Permite responder rápidamente al webhook.
- Facilita reintentos y manejo de errores.
- Absorbe picos de tráfico.
- Permite escalar consumidores independientemente.

**Desventajas:**
- Agrega infraestructura y complejidad operativa.
- La comunicación pasa a ser eventualmente consistente.
- Requiere contemplar mensajes duplicados e idempotencia.

### Procesamiento mediante tareas internas en memoria

El webhook podría colocar los mensajes en una cola interna del proceso.

**Ventajas:**
- Menor complejidad que RabbitMQ.
- No requiere un broker externo.

**Desventajas:**
- Los mensajes se perderían si el proceso se reinicia.
- No permite escalar fácilmente a múltiples instancias.
- No cumple con el requisito explícito de utilizar RabbitMQ.

## Decisión

Se utilizará RabbitMQ para desacoplar la recepción del webhook de Telegram del procesamiento de los mensajes entrantes.

El flujo será:

```text
Telegram
   ↓
Webhook HTTP
   ↓
Validación mínima
   ↓
RabbitMQ
   ↓
Consumer
   ↓
Procesamiento de dominio
   ↓
PostgreSQL
   ↓
SignalR
   ↓
Angular
```

El endpoint del webhook tendrá como responsabilidad principal:

1. Recibir el update de Telegram.
2. Validar que el payload sea correcto.
3. Publicarlo en RabbitMQ.
4. Responder exitosamente a Telegram.

La lógica de creación o actualización de contactos, conversaciones y mensajes se ejecutará en un consumidor separado.

### Topología de RabbitMQ

Se utilizará un exchange:

```text
telegram.incoming
```

Una cola principal:

```text
telegram.incoming.messages
```

Y una routing key:

```text
telegram.message.text
```

También se configurará una Dead Letter Queue:

```text
telegram.incoming.messages.dlq
```

Los mensajes que no puedan procesarse correctamente después de los intentos definidos podrán enviarse a esta cola para su análisis posterior.

Para esta prueba se utilizará una topología simple, evitando crear múltiples exchanges o colas que no aporten valor al alcance actual.

## Idempotencia

Telegram puede reenviar un update si no recibe una respuesta válida o ante determinadas condiciones de red.

Por este motivo, el procesamiento no asumirá que cada mensaje recibido es único.

Se almacenará el identificador del update enviado por Telegram (`update_id`) y se aplicará una restricción única en base de datos.

Antes de procesar un update, el sistema verificará si ya fue registrado.

De esta forma se evita:

- Persistir el mismo mensaje más de una vez.
- Incrementar incorrectamente el contador de mensajes no leídos.
- Enviar eventos duplicados al frontend.

## Confirmación del mensaje

El consumidor confirmará (`ack`) el mensaje de RabbitMQ únicamente después de completar correctamente el procesamiento y la persistencia correspondiente.

Ante un fallo inesperado, el mensaje podrá ser rechazado o reenviado según la política configurada.

La notificación mediante SignalR se realizará después de confirmar la persistencia en base de datos, evitando que el frontend visualice mensajes que no hayan sido almacenados correctamente.

## Consecuencias

La solución obtiene un mayor desacople entre Telegram y la lógica interna de la aplicación, además de una mejor tolerancia a fallos y capacidad para absorber variaciones en el volumen de mensajes.

Como contrapartida, se incorpora complejidad adicional al introducir un broker de mensajería y procesamiento asíncrono.

También es necesario diseñar los consumidores para que sean idempotentes, ya que RabbitMQ ofrece entrega al menos una vez y un mensaje podría ser procesado más de una vez.

Para el alcance actual, una única cola de mensajes entrantes y una Dead Letter Queue proporcionan suficiente resiliencia sin introducir una topología innecesariamente compleja.
