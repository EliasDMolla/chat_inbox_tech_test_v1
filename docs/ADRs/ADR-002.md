# ADR-002: Comunicación en tiempo real con SignalR

**Estado:** Aceptado

## Contexto

La bandeja conversacional necesita reflejar en tiempo real los mensajes recibidos desde Telegram y los cambios de estado de las conversaciones, por ejemplo la actualización del último mensaje o la cantidad de mensajes no leídos.

El frontend debe recibir estas actualizaciones sin depender de polling periódico contra la API, evitando tráfico innecesario y demoras en la experiencia del operador.

## Alternativas consideradas

### SignalR

Permite comunicación en tiempo real entre ASP.NET Core y clientes web, utilizando WebSockets cuando están disponibles y gestionando automáticamente mecanismos alternativos cuando es necesario.

**Ventajas:**
- Integración nativa con ASP.NET Core.
- Cliente oficial para JavaScript/TypeScript.
- Manejo de reconexión y transporte abstraído.
- Reduce la complejidad de implementar WebSockets manualmente.
- Facilita el envío de eventos específicos al frontend.

**Desventajas:**
- Genera cierto acoplamiento con el ecosistema .NET.
- Para escenarios distribuidos con múltiples instancias puede requerir infraestructura adicional, como Redis o Azure SignalR Service.

### WebSockets directos

Permiten una conexión bidireccional persistente entre frontend y backend.

**Ventajas:**
- Menor nivel de abstracción.
- Control completo sobre el protocolo y los mensajes.

**Desventajas:**
- Requieren implementar manualmente reconexión, gestión de conexiones y manejo de errores.
- Agregan complejidad que no aporta valor para el alcance de esta solución.

### Server-Sent Events

Permiten comunicación unidireccional desde el servidor hacia el cliente.

**Ventajas:**
- Simples de implementar.
- Adecuados para notificaciones servidor-cliente.

**Desventajas:**
- Solo permiten comunicación unidireccional.
- Ofrecen menor flexibilidad frente a posibles necesidades futuras de comunicación bidireccional.

### Polling

El frontend consulta periódicamente la API para detectar nuevos mensajes.

**Ventajas:**
- Implementación simple.
- No requiere conexiones persistentes.

**Desventajas:**
- Genera solicitudes innecesarias.
- Introduce latencia entre la recepción del mensaje y su visualización.
- Escala peor a medida que aumenta la cantidad de operadores o conversaciones.

## Decisión

Se utilizará **SignalR** como tecnología de comunicación en tiempo real entre el backend y el frontend.

Después de que un mensaje entrante sea procesado y persistido correctamente, el backend emitirá un evento mediante SignalR para actualizar la interfaz.

Los principales eventos previstos son:

- `MessageReceived`
- `MessageSent`
- `ConversationUpdated`
- `MessagesRead`

Los eventos se emitirán únicamente después de confirmar la persistencia en la base de datos, evitando mostrar en el frontend información que todavía no haya sido almacenada correctamente.

## Consecuencias

SignalR permite implementar una experiencia de actualización inmediata con una complejidad reducida y buena integración con el stack elegido.

Se evita el polling y se centraliza la comunicación en tiempo real dentro del backend.

Como contrapartida, la solución queda parcialmente ligada al ecosistema ASP.NET Core. Además, en un escenario futuro con múltiples instancias del backend sería necesario incorporar un mecanismo de coordinación distribuida, como Redis Backplane o Azure SignalR Service.

Para el alcance actual, donde la aplicación se ejecuta mediante Docker Compose en una única instancia, esta limitación no representa un problema.

Las notificaciones se envían a `Clients.All` porque el alcance contempla un solo operador. SignalR es best effort y PostgreSQL continúa siendo la fuente de verdad: un fallo de notificación posterior al commit no revierte la persistencia, y el cliente rehidrata conversaciones e historial desde la API después de una reconexión. No se incorpora Outbox ni backplane en esta prueba.
